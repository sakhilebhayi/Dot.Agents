### Dot.Memory / Dot.Brain integration
**Phase 0 finding (confirmed none of it existed):** the only reference to "Dot.Memory" anywhere in the codebase was a decorative link in `config/ecosystem.php:35`. `MemoryService`/`AgentMemory` and `EnterpriseBrainService` share vocabulary with the platform contract but are unrelated local features.

✅ **Phase 4 built 2026-09-19 — but first corrected a wrong assumption in the original contract brief.** `Dot.Brain/platforms/dot-agents.md` describes calling Dot.Brain endpoints (`retr:agent-context:hot`, DKP publishing) — but **Dot.Brain has no running service at all**: no `composer.json`, no server, nothing listening on any port. It is a documentation/knowledge-graph specification repo; `brain.api.md`'s `POST /v1/dkp` etc. describe an aspirational API that doesn't exist anywhere yet. Any code calling it would be calling a URL with nothing on the other end. **Dot.Memory, by contrast, is real and running**, with a genuine, live "Intelligence Loop" API (`/api/intelligence/{events,decisions,actions,outcomes,context}`, Sanctum-token auth) — confirmed by reading `Dot.Memory/app/Http/Controllers/Intelligence/LoopController.php` directly.

Given this, Phase 4 built two real things instead of one fictional one:

1. **`App\Services\Memory\DotMemoryClient`** — a real HTTP client for Dot.Memory's live Intelligence Loop API. `recordEvent`/`recordDecision`/`recordAction`/`recordOutcome` fail closed (never throw; return `false` on any failure, including "not configured" — expected in this dev environment since `DOT_MEMORY_API_URL`/`DOT_MEMORY_API_TOKEN` aren't set). `context()` is the deliberate exception: it returns `null` on ANY failure, and that `null` is the contract-mandated "degraded" signal, kept distinct from a legitimate empty/unknown-subject response. Wired into `AgentOrchestrationService::executeTask()`: `context()` is called before the model runs and the result is persisted as `AgentTask.metadata['dot_memory_context_degraded']` (true/false, always set, verified live in browser); `recordDecision`/`recordAction` fire right after the real `DecisionLog::create()` call, sharing one loop UUID per task.

2. **`App\Services\Governance\AgentCharterLoader`** — reads Dot.Brain's real charter files (`agents/*.charter.md`, YAML frontmatter parsed with Symfony's YAML component) directly from disk (`config('services.dot_brain.charters_path')`, documented as a local-monorepo assumption — a real multi-host deployment would need a git-sync or API instead, neither of which exists today). **Honest, confirmed finding: every current Dot.Agents marketplace agent (CEO Agent, Financial Analyst, etc.) comes back uncharted** — Dot.Brain's charters are for a separate, ecosystem-wide "colony agent" roster (governance, finance, documentation, etc. — abstract domain roles maintaining Dot.Brain's own knowledge graph), not Dot.Agents' commercial catalog. This is not a bug; it correctly triggers the contract's own fallback rule.

3. **Colony runtime contract, enforced for real** in `executeTask()`: an uncharted agent (the default, for everything today) has `requires_human_approval` unconditionally forced to `true` regardless of confidence/delusion scores (`runc:provisional`'s "all recommendations escalated" rule) — **verified live**: running a real workflow node now correctly lands the task in `awaiting_approval` and creates a real, visible `AgentApproval` row. A chartered-but-below-`trust-score-floor` agent gets the same forced approval (the charter template's own probation rule). Resource bounds — `config('services.dot_brain.provisional_wall_clock_ms', 60000)` and `provisional_max_tool_calls`, 5 — are checked after the model call for provisional agents only; a breach dispatches a new real `AgentRunContractBreach` event and reuses the existing `DigitalImmuneSystem` deployment-suspension mechanism (no new suspension logic written).

4. **Two new real domain events**: `AgentRunContractBreach` (audit-logged via a new listener) and `AgentCharterDriftDetected` (event + listener plumbing built and real, but **no automated detector exists behind it** — charters are prose today with no structured, machine-comparable scope field, so this can only be dispatched manually until charters gain structured data; documented honestly in the class docblock rather than faking a check). A third planned event, `AgentEscalationRaised`, was **not** added — `ApprovalRequested` already fires at approval-creation time and covers the same gap; adding a duplicate would have been redundant.

**What was explicitly NOT built, and why:** DKP knowledge-pack publishing (`POST /v1/dkp`) and escalation routing to Dot.Notify — neither has a real, running endpoint anywhere in this ecosystem today. Building code to call them would be reintroducing exactly the kind of silent-stub problem this whole audit-and-fix engagement has been closing. These stay as real, documented gaps rather than fake integrations.

### Database portability (sqlite vs. the real Postgres deployment)
**This is the most important infrastructure finding of the whole audit+fix pass, and it was invisible to the entire 900+ test suite.** The test suite runs against sqlite (`:memory:`), but the real dev/prod database is Postgres (`DB_CONNECTION=pgsql`). Two classes of bug only manifest on Postgres and were only found by manually running the app against the real Postgres dev DB in a browser:
1. **Double-quoted SQL string literals** (`status = "completed"`) — valid on lenient sqlite/MySQL, a hard error on strict Postgres (which treats `"..."` as an identifier, not a string). Found and fixed in 5 places across `AgentReputationService` (×3), `SocialCommerceService`, and `EnterpriseBrainService`.
2. **`strftime()`** — a SQLite-only date function with no Postgres equivalent. Found and fixed in `SlaMonitoringDashboard` and `SlaAnalyticsService`, using the driver-aware date-expression pattern already established in `FinancialTrendAnalyzer` (a per-driver constant map + a small `dateExpr()` helper, rather than inventing a new abstraction).

A grep sweep (`grep -rnE '= "[a-z_]+"' app/` plus a check for `strftime`/`IN ("`/`LIKE "`) found no further occurrences of either pattern as of 2026-09-16, but **this class of bug can reappear** any time new raw SQL is added — see the recommendation below.

### Local dev/pilot database drift (informational, not a code bug)
The `dot_agents_pilot` Postgres database's `migrations` table recorded `2026_06_12_165902_create_permission_tables` as already run, but the actual `permissions`/`roles`/`model_has_roles` tables didn't exist — a pre-existing drift between the migration ledger and real schema, unrelated to any change in this session. Repaired by directly invoking that migration's `up()` (pure `CREATE TABLE`, no data loss). This is purely a local-environment fix, not an application bug.

### Test coverage
Suite is large (~150+ files) and the sampled files use real `assertDatabaseHas`/`assertDispatched`/state assertions, not bare status-code checks. Confirmed gaps: no test exercised `ModelRouterService::buildFailoverChain()` directly (now covered), and — more significantly — **the suite cannot catch Postgres-specific SQL errors at all**, since it never runs against Postgres. Recommend adding a CI job (or a local `composer test:pgsql` script) that runs the suite against a real Postgres instance, even just periodically — every bug in the "Database portability" section above would have been caught immediately by that alone.
